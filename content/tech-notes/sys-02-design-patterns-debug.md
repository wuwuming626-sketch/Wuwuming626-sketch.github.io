## 机制与原理

### 单槽最后状态执行模型

系统中存在大量“最终状态驱动”的操作（LED/GPIO 控制、网络通断汇报、快速 Hold/Resume、配置文件保存、数据库模糊查询）。它们的共同特征是：外部事件可能高频触发同类请求；系统只关心最后一次请求的结果；中间状态可以完全丢弃。用普通队列、防抖延时或直接调用去实现，容易出现队列堆积、重复执行、竞态或响应不及时。

为此抽象出统一的轻量并发模型，包含四个关键机制：

1. **单槽队列 / 单槽事件**：每个独立任务拥有容量为 1 的槽位。新请求到达时无条件覆盖槽内旧请求；无请求时槽位为空。
2. **阻塞等待**：消费者在槽位为空时挂起，不消耗 CPU；生产者写入后立即唤醒消费者。
3. **执行后追赶**：消费者完成一次实际工作后，必须立即检查槽位中是否又有新请求（即执行期间到达的请求）。若有，则丢弃刚才的工作结果并按新请求重新执行；若无，则回到阻塞等待。
4. **状态比较优化**：若新请求内容与刚执行的请求相同，消费者可跳过重复执行直接回到等待状态。

平台层提供两类标准化同步原语，业务模块禁止自行实现队列、信号量或防抖逻辑：

| 原语 | 用途 | 关键操作 |
|------|------|----------|
| 带数据的单槽队列 | 请求需携带参数（LED 目标状态、查询关键词等） | 提交（覆盖并唤醒）、阻塞取出、非阻塞尝试取出 |
| 无数据的单槽事件 | 纯通知（保存配置、网络状态变化） | 触发（置位且不堆积）、阻塞等待（返回后自动清除）、非阻塞尝试等待 |

**适用**：二值状态控制（LED 亮/灭、继电器吸合/释放、电机启停）、二值状态汇报（网络在线/离线、故障与否、门开/关）、快速切换（播放/暂停、Hold/Resume、静音）、防抖类操作（模糊查询、配置保存），以及任何“只关心最终结果”的工作。

**不适用**：需严格顺序处理的命令序列（如串口指令流）、每次请求都有独立且不可覆盖效果的操作（计数累加、单次扣款、发邮件）、需完整记录每次变化的审计日志。

**内存归属**：单槽队列中的数据遵循“生产者负责分配、消费者负责释放”；执行追赶中被丢弃的数据同样由消费者释放。

### 临界区与锁的使用约束

核心原则是操作系统并发编程的共性问题——**锁的层次嵌套与调度器语义冲突**：任务持有锁 A 时调用某函数，该函数为保护自身资源需要获取锁 B，即形成锁嵌套；若另一任务持锁 B 又需要锁 A，则构成 **ABBA 死锁**。

单核与多核的表现差异：单核下持自旋锁或进入临界区通常关中断 / 锁调度器，只要执行路径足够短可能侥幸通过；SMP 下多个核心物理并行，ABBA 死锁从“概率事件”变为“统计必然事件”，一旦发生系统立即冻结。

基本原则：在持有互斥量、自旋锁或处于关中断临界区期间，临界区代码必须满足全部条件——执行时间极短且可预测（微秒级）、不调用任何可能阻塞当前任务的函数、不调用任何可能获取其他锁（显式或隐式）的函数、不触发任何任务切换。

四条红线规则：

| 规则 | 禁止内容 | 典型函数 |
|------|----------|----------|
| 一 | 动态内存堆操作 | `malloc`/`calloc`/`realloc`/`free`、`pvPortMalloc`/`vPortFree`、`rt_malloc`/`rt_free`、`kmalloc`/`kfree`/`vmalloc` |
| 二 | 阻塞型 IPC | `xQueueSend`/`xQueueReceive`/`xSemaphoreTake`/`vTaskDelay`/`xEventGroupWaitBits`、`rt_sem_take`/`rt_mq_recv`/`rt_thread_delay`、`k_queue_get`/`k_sem_take`/`k_sleep`、`pthread_mutex_lock`/`sem_wait` |
| 三 | 隐式加锁的库函数 | `printf`/`puts`/`fwrite`（stdout 流锁）、`gettimeofday`/`localtime`/`clock_gettime`（全局时间锁）、自定义 `LOG_INFO`/`log_printf`、C++ 容器 `push_back`/`insert`（可能内存分配） |
| 四 | 临界区过长 | 只允许简单算术、变量赋值、链表指针挂摘、位操作；超过 20 行或含循环即视为违规 |

违规后果分别为：堆管理器锁与外部锁嵌套触发 ABBA 死锁；持锁进入阻塞态导致锁永不释放（FreeRTOS 中持自旋锁调用 `vTaskDelay` 会直接触发硬件异常）；形成不可预见的网状锁依赖链，偶发随机死锁且极难复现；关中断过久导致中断延迟超标、外设丢数据，长持锁导致高优先级任务饥饿。

该约束跨操作系统、跨架构普遍成立：FreeRTOS（SMP 下 ABBA 必然发生）、RT-Thread（V5.1.0 后明确禁止嵌套阻塞 IPC）、Linux 内核（互斥量是睡眠锁，自旋锁下不能睡眠）、Linux 用户空间（glibc 堆锁）、Zephyr、VxWorks 均按“高危 / 绝对禁止”处理。

### 自旋锁中的内存屏障语义

结论先行：**DMB 管“顺序”，DSB 管“完成”**。

- **DMB** 是顺序约束：DMB 之前的 load/store 不能重排到其后，之后的 load/store 不能重排到其前。它不保证语句严格按源码顺序执行，也不等价于“远端立即可见”。
- **DSB** 是最终同步：它之前完成的 store 必须真正完成，之后才允许继续执行下一步动作（另一核继续执行、DMA/外设读状态、wakeup/event/interrupt、释放锁后进入下一阶段）。

以获取锁为例：

```c
slock->core_id = core_id;
slock->count = 1;
__DMB();
return 1;   /* 拿锁成功，调用方接下来进入临界区 */
```

这里的 `return 1` 语义不是“函数逻辑结束”，而是“拿锁成功，调用方接下来会走临界区”。若不加 DMB，部分指令可能被重排到 return 之前，导致“锁状态还没稳定，调用方已经访问受保护对象”的语义错误。因此 DMB 的意义在于让“锁状态已写好”与“调用方后续临界区访问”之间不能发生错误重排，而不是让远端马上可见。

以释放锁为例：

```c
slock->core_id = SPINLOCK_CORE_ID_UNINITILIZE;
__STL(0, (uint32_t *)&slock->owner);
__DSB();
__SEV();
```

关键语义是：先完成前面的写入，再让其他观察者看到最终状态，然后才发事件唤醒等待者。因此该 spinlock 代码中“获取锁用 DMB、释放锁用 DSB”，是符合 SMP 共享状态语义的标准做法。

选择依据：需要“先写状态、再使用状态”的顺序边界时用 DMB；需要在锁释放、状态变更、事件通知之前保证前面的写入已经落地，且后续动作（其他核 / DMA / 外设观察）依赖这些写入时用 DSB。

### errno 的错误码语义（SMP）

`errno` 是进程/任务级全局错误码，被并发执行流共享。源文档用三组 CLI 实验验证了当前平台在 SMP 配置下的行为：

- 单核场景：两个线程绑同一核心顺序执行，先写后读不会被“另一核”即时覆盖；
- 双核场景：两个线程分别绑 `core0`/`core1`，同一并发窗口内 B 的写入会覆盖 A 的结果；
- 更强的一点：**即使业务层在 syscall 返回后立即缓存 errno，也未必拿到真实值**——`recv()` 这类封装函数内部如果继续执行额外逻辑，`errno` 可能在封装函数内部后处理阶段已被其他执行流改写。

由此得到的编码原则是：应在**最底层真实错误产生点**尽早缓存 / 传递稳定结果，而不是在业务层依赖“刚返回时读一次 errno”。

### 调用栈回溯与日志手段

- **CmBacktrace（FreeRTOS 调用栈回溯）**：MIT 许可证、纯 C、资源占用极低（ROM 约 3 KB、RAM < 1 KB）。能力分两类：被动捕获（自动接管 HardFault、MemManage 等异常，输出崩溃任务调用栈，MPU 越界同样触发）；主动查询（`cm_backtrace_call_stack()` 传入任意任务栈地址与大小，获取其调用栈地址列表）。集成需小幅修改 FreeRTOS 内核 TCB。
- **异步日志**：临界区内仅把日志数据写入无锁环形缓冲区，解锁后由后台低优先级任务统一执行 `printf`，避免在持锁区间调用可能加锁的 I/O 函数。
- **协议抓包**：`hcidump -w log.cfa &` 捕获并记录 HCI（Host Controller Interface）流量；导出后由 Wireshark 解析。
- **硬件信息查询**：`aexnc hw info "<key>"`，可直接读取 `memTotal` / `memFree` / `memAvail` / `wanSpeed` / `lanSpeed` / `sdOn` 等运行态信息。

## 技术流程与使用方式

### 单槽模型的模块改造流程

1. **模块梳理与识别**：逐一检查所有可能被高频触发、且只关心最终结果的操作点；列出当前实现方式（队列 / 延时 / 直接调用 / 轮询标志）与问题（堆积、重复执行、竞态）；对照适用性标准确认是否改造，不适用需记录理由。
2. **生产者侧改造**：移除直接调用执行函数或发消息队列的代码，改用平台的“单槽队列提交”或“单槽事件触发”；生产者不持有任何锁、不做长耗时操作。
3. **消费者侧改造**：为每个独立操作建立专用消费者任务，主循环固定为四步——
   - 阻塞取出请求（队列）或阻塞等待事件；
   - 执行实际工作（控制硬件、查询数据库、保存文件）；
   - 立即追赶检查：队列用“非阻塞尝试取出”，取到且与刚执行的数据不同则丢弃旧结果、跳回上一步；事件用“非阻塞尝试等待”，成功则丢弃旧结果、跳回上一步；
   - 追赶无新请求则回到阻塞等待。
   消费者执行工作期间不得持有平台队列/事件的内部锁。
4. **移除冗余代码**：删除自实现的队列、缓存、环形缓冲区、防抖定时器与延时函数、多余状态标志与手动同步原语、历史遗留的重复执行或漏执行补偿逻辑。
5. **测试与验证**：高频压力测试（极短时间内连续触发大量请求，确认只执行最后一次且无泄漏 / 死锁 / 崩溃）、多生产者并发提交测试、空闲功耗验证（消费者确实挂起、无忙等待）、状态比较优化验证（连续提交相同状态应跳过）。
6. **文档更新**：标注使用了平台单槽模型，说明消费者任务优先级、栈大小及与生产者的交互关系，记录改造前后性能对比。

改造的典型形态（无代码）：LED 控制由“按键中断直接写 GPIO”改为“中断提交状态 + 专用任务设置 GPIO”；网络状态上报改为单槽事件，保证最终上报与实际一致；配置保存由多处直接写 Flash 改为统一的单槽事件触发；数据库模糊查询按最后一次关键词执行。

自检清单：适用操作均已识别改造 / 每个独立操作有专属单槽原语 / 生产者无直接调用 / 消费者遵循“阻塞等待 → 执行 → 追赶检查 → 循环” / 旧队列与延时已删除 / 压力与并发测试通过 / 空闲时消费者确实挂起 / 设计文档已更新。

### 临界区的合规写法

- **发送 / 入队（内存申请）**：先在锁外 `malloc` 并填充数据 → 获取锁 → 仅挂入链表（指针操作）→ 立即释放锁。锁的持有区间不含任何内存管理操作。
- **接收 / 出队（内存释放）**：获取锁 → 摘下节点指针 → 立即释放锁 → 锁外做数据拷贝 → 锁外 `free`。
- **日志打印**：使用异步日志，临界区内只写无锁环形缓冲区，解锁后统一输出。

### 任务调用栈回溯的接入与使用

实施要点有两处：其一，修改 `tasks.c` 中 TCB 结构体，增加 `uxSizeOfStack` 成员，并提供辅助函数 `vTaskStackAddr()`、`vTaskStackSize()`、`vTaskName()`；其二，按需选择使用方式。

方式一（崩溃时自动打印）：集成后无需额外代码，MPU 越界或 HardFault 发生时自动输出崩溃任务调用栈。

方式二（主动查询指定任务）：

```c
TaskHandle_t xTask = xTaskGetHandle("TaskName");
uint32_t stack_addr = (uint32_t)vTaskStackAddr(xTask);
uint32_t stack_size = vTaskStackSize(xTask);
uint32_t call_stack[16];
size_t depth = cm_backtrace_call_stack(call_stack, 16, stack_addr, stack_size);
/* 打印 call_stack 数组 */
```

可在调试控制台、定时器或低优先级任务中实现“查询所有任务调用栈”的命令。输出为地址，用 `addr2line -e firmware.axf <address>` 可解析为文件名与行号。

典型调试用法：MPU 越界崩溃 → 自动输出崩溃任务调用栈；任务死锁 → 主动查询所有阻塞态任务的调用栈，观察其等待位置；任务卡死 → 定期打印当前运行任务的调用栈，定位死循环或阻塞点；栈溢出风险 → 结合高水位线与调用栈深度预估。

### 代码提交与评审流程

1. 拉取代码：`repo init` 指定内网 Git 服务器上的 repo 镜像与 manifests 仓库及对应 XML，然后 `repo sync`；若需切换平台分支，则修改 `.repo` 下 `manifest.xml`（删除原链接后建立指向目标分支 XML 的符号链接），再执行 `repo sync -c`（`-c` 只同步当前分支，节省时间与带宽）。同步报错时可进入对应子仓库执行 `git checkout .` 丢弃未提交改动后重试。
2. 本地提交前的自查：`git status` 查看被修改文件；`git diff <file>` 确认仅保留必要改动；`git log` 参考既有提交信息风格。
3. 建立分支：`git checkout -b <user>_T104135_AIC_BT_ERROR`（分支名含问题单号与简短描述），再用 `git status` 确认当前分支。
4. 暂存与提交：`git add <file1> <file2> ...`（多个文件以空格分隔），`git commit -m "[user][T104135][v65][bug]:修复蓝牙关闭后仍能扫描问题"`。
5. 复核与推送：`git show` 查看最新提交的哈希、作者、日期、提交信息与本次 diff；`git push <remote> <branch>:refs/for/<target_branch>` 推送到评审分支（未建分支时可用 `HEAD`）。
6. 提交失败的一种典型情况：项目目录缺少推送钩子工具，需要先获取并放置对应工具（`python3 repo_get_hook.py`）后重新推送。

### 仅 ADB、权限受限环境下的验证流程

前提：设备通过 USB 连接、`adb devices` 可见；先尝试 `adb root`，失败（如提示 `adbd cannot run as root`）则保持普通 shell，后续按“有 root / 无 root”区分。

- **验证一：eth0 是否因未 up 而无 IP**。顺序为 `ip addr show eth0`（记录是否有 `inet`、是否 `state DOWN`）→ 插网线后再看一次 → `ip link set eth0 up`（若报 `Operation not permitted` / `Permission denied` 则记下完整报错并跳过后续可写步骤）→ 再 `ip addr show eth0` 看是否 `state UP` 且出现 `inet`（DHCP 可能需数秒到十几秒，可多执行几次）→ `getprop | findstr dhcp` 看是否曾有 IP 属性 → `ping -c 3` 公网地址或网关。若手动 up 后拿到 IP 且能 ping 通，即可判定“eth0 缺的是开机时未被 up”。
- **验证二：抓 SELinux/内核日志**。先试 `adb shell dmesg > dmesg_after_reboot.txt`，成功后在本机搜索 `avc`、`wifi`、`eth0`、`stmmac`、`denied`；无权限则改用 `adb logcat -d -b all > logcat_after_reboot.txt`（重启后尽快执行，避免日志被刷掉），搜索 `avc`、`denied`、`wifi-service`、`Permission denied`、`eth0`、`EthernetNetworkFactory`，把命中片段单独存成文本交系统/BSP 同事。部分机型还可读 `/sys/fs/selinux/avc/threshold` 或用 `adb logcat -b events -d` 过滤 `avc`。
- **验证三：确认 init 是否配置了 up_eth0**。尝试 `cat /system/etc/init/hw/init.rc`，失败则查 `/vendor/etc/init/` 下的 rc 文件，在本机搜索 `up_eth0`、`eth0`、`busybox`；读不到则记录“需在源码/设备树侧搜索 up_eth0、busybox”。

汇总输出格式：逐项填写“执行结果（成功/失败与报错原文）”，并附一句“当前仅能使用 ADB，部分操作无权限；上述为在现有权限下能做的全部验证”。也可用一条龙命令一次性执行并把全部输出（含报错）重定向保存为完整验证记录。

## 调试过程记录

### 案例一：蓝牙关闭后仍可被扫描到（问题单 T104135）

**现象**：在蓝牙打开状态下，手机可正常扫描到话机蓝牙；执行 `hciconfig hci0 down` 关闭后，手机蓝牙列表**仍能扫描到**话机蓝牙；而执行 `hciconfig hci0 noscan` 后手机就扫描不到了。

**定位手段一：命令矩阵缩小范围**。先用 `hciconfig -a` 枚举设备（确认设备名为 `hci0`），再用 `up` / `down` / `reset`、`piscan` / `iscan` / `pscan` / `noscan`、`name`、`class`、`features`、`version`、`commands` 等子命令确认 up/down 与扫描开关的行为差异，判定问题出在 down 路径未真正关闭射频侧行为，而非扫描参数配置。

**定位手段二：HCI 抓包**。在设备侧执行 `hcidump -w log.cfa &`（`hcidump` 监控 HCI 数据包，`-w` 以二进制 CFA 格式写入 `log.cfa`，`&` 放后台），采集不同平台（v65 平台与 w620w 平台）的日志后取回本机分析：一路用 `tftp -r log.cfa -p 10.0.0.20` 上传到电脑，一路用 `adb pull /userdata/log.cfa ./` 拉到当前目录。随后用 Wireshark 打开，按“扫描到的蓝牙设备 MAC 地址”逐次比对两次扫描结果，定位到关闭后仍存在可被发现的响应流量。

**定位手段三：追调用链**。关闭流程自用户空间 `hciconfig hci0 down` 经 Socket 进入内核：`ioctl()` → `vfs_ioctl()` → `sock_ioctl()`；蓝牙设备通过 Socket 接口抽象，最终路由到 `net/bluetooth/hci_sock.c` 的 `hci_sock_ioctl()`（处理 `HCIDEVDOWN`）并调用 `net/bluetooth/hci_core.c` 中的 `hci_dev_close()`，后者调用 `hci_dev_do_close()` 执行实际关闭，再下沉到蓝牙模组驱动层。

**定位手段四：模组使能脚与驱动接口对比**。通过调试文件系统查看 GPIO（`cat sys/kernel/debug/gpio`），用 `export` / `direction` / `value` 节点手动拉高拉低测试模组使能脚，并 `insmod ./config/modules/4.9.84/aic_load_fw.ko` 观察模组行为。对比后发现：`aci_btusb` 模块在 down 时会先调用 `btusb_shutdown` 接口、再调用 `btusb_close`；而 `btusb` 驱动相比 `aci_btusb` **缺少 `btusb_shutdown` 接口的相关操作**。

**根因**：`hciconfig hci0 down` 先执行软件关闭，随后触发蓝牙模组驱动接口。由于原代码没有实现 `btusb_shutdown`，硬件关闭动作没有被执行，只完成了软件关闭，因此 down 之后射频侧仍然可被其他设备扫描到。

**修改**：补上 `shutdown` 接口函数实现。改动文件为 `drivers/bluetooth/btusb.c` 及相邻的 `drivers/bluetooth/Kconfig`、平台 `defconfig`。

**验证结论**：补上该接口后问题解决。本地提交按“查看改动 → 仅暂存必要文件 → 提交 → `git show` 复核 → 推送到评审分支”的流程完成，提交信息中标注问题单号、平台与 bug 类型。

### 案例二：errno 在 SMP 下被并发覆盖

**现象**：网络断开路径中，`peerClosedSocket()` 读到的 `errno` 与底层实际错误不一致。

**定位手段一：最简 CLI（`errno_test smp_simple`）**。设计两组用例：`single_core`（A、B 线程均绑 `core0`，A 先写 `errno = 1111`，B 再写 `errno = 2222`，A 最后读回）与 `dual_core`（A 绑 `core0`、B 绑 `core1`，时序相同）。实测输出：

```text
[errno][INFO] single_core A=1111->1111 B=2222->2222
[errno][INFO] dual_core   A=1111->2222 B=2222->2222
[errno][PASS] smp_simple single_core keeps errno=1111, dual_core overwrites errno=2222
```

结论：单核顺序执行下未发生覆盖，双核并发下 A 读回的是 B 写的 `2222`，即全局 `errno` 被另一核上的执行流覆盖。

**定位手段二：统计 CLI（`errno_test smp_race [loops]`）**。用高频握手统计证明该现象不是偶发：

```text
[errno][PASS] smp_race observed overwrite(handshake): loops=1 total=1
              A(mismatch=1 first_iter=0 first_seen=2222) B(mismatch=0 first_iter=-1 first_seen=0)
```

`loops=1` 即命中覆盖，说明这是机制上成立的结果，而非依赖复杂时序的低概率事件。

**定位手段三：反证实验（core0 注入线程）**。开机启动一个 `core0` 干扰线程，平时空转/阻塞；`peerClosedSocket()` 进入前拉高全局标志 `g_errno_inject_on = 1`，干扰线程看到标志后持续执行：

```c
errno = 125;
```

退出时清掉标志。实测日志显示：lwIP 真正返回的是 `mapped_errno=11`（`Operation would block.`），而 `peerClosedSocket()` 最终读到的却是 `recv_errno=125`。

**根因**：后续读到的 `errno` 已被并发执行流覆盖，不再代表本次 `recv` 的真实结果。进一步地，问题不限于“另一个核在 syscall 返回后立即改写”，还包括封装函数内部在真实错误产生后继续执行额外逻辑，导致活 `errno` 被污染。

**修改与验证结论**：`n = recv(...); saved_errno = errno;` 这种“立即缓存”写法只在调用链保证“函数返回前不会再改 errno”时有效；对本次问题，正确做法是把稳定结果尽可能保存在**最底层真实错误产生点**（例如 lwIP 内部真实错误转换点），而不是依赖业务层在 syscall 返回后读取。

### 案例三：eth0 无 IP 与 SELinux 日志采集（仅 ADB）

**现象**：设备只能通过 ADB 访问，且大量操作无权限；需要判断 eth0 是否为“接口未被 up”导致无 IP，并收集 WiFi/eth0/avc 相关日志供 BSP 写策略。

**定位手段**：按第 3.6 节的三步验证执行——先只读观察 `ip addr show eth0` 与 `getprop | findstr dhcp`、`ping`；再尝试写操作 `ip link set eth0 up`；同时尝试 `dmesg` 导出，无权限时退化为 `logcat -d -b all` 并按 `avc`、`denied`、`wifi-service`、`eth0`、`EthernetNetworkFactory` 等关键字过滤；最后尝试读取 init 配置确认是否存在 `up_eth0` 服务。

**处理原则与结论**：源文档给出的不是定论而是可执行的取证路径——若手动 up 后能拿到 IP 且能 ping 通，则支持“eth0 缺的是开机未被 up”的假设；若写操作被拒，则记录“无 root、无法执行 `ip link set eth0 up`，请在有权限环境复验或由 BSP 在镜像中修复”；无论哪种结果，都把可读到的 dmesg / logcat 片段与权限错误原文一并提供，并明确声明“当前仅能使用 ADB，部分操作无权限”。

### 案例四：任务死锁 / 卡死的定位套路

对 FreeRTOS 系统，除了依赖 MPU 越界等崩溃场景的自动回溯外，还需要主动查询任意任务调用栈。操作要点：

1. 对疑似死锁，主动查询所有阻塞态任务的调用栈，观察各自等待位置，判断是否互相等待同一把锁；
2. 对任务卡死或长时间阻塞，定期打印当前运行任务的调用栈，定位死循环或阻塞点；
3. 对优先级翻转，结合调用栈与任务优先级/持锁关系分析；
4. 对栈溢出风险，结合高水位线与调用栈深度预估。

注意：主动查询时目标任务必须处于挂起或阻塞状态，否则其栈内容可能被动态修改；若必须查询运行中任务，可先挂起再查询。

## 结论与注意事项

1. **单槽模型是“最终状态驱动”问题的标准范式**。改造的收益来自三点：消除无效中间执行、消除竞态、把同步语义收敛到平台原语。两个易错点需要留意——工作耗时较长时，追赶丢弃旧结果并不等于工作函数立即停止，需要在工作函数内部实现“取消”或“过期检查”（例如为每次执行分配递增序列号，完成时比对当前请求序列号，不一致则丢弃结果）；不同操作不建议共用同一消费者任务，避免相互影响与优先级反转。中断服务程序中可以调用提交/触发接口，但需保证接口本身是中断安全的（自旋锁或屏蔽中断），建议中断中只触发无数据事件，数据准备放到任务中。若某操作即使状态相同也必须执行（例如“刷新”），则不应使用本模型。
2. **持锁期间的问题不是“某操作系统特有的”，而是并发编程的基本原理**。锁的持有区间必须只包含指针操作、赋值与位运算；任何内存管理、阻塞 IPC、隐式加锁的库调用都应移到锁外。
3. **内存屏障的选型看问题类型**：关心跨 barrier 的乱序 → DMB；关心前面写入是否真正落地并据此唤醒/通知对端 → DSB。获取锁用 DMB、释放锁用 DSB 是自旋锁实现中的常见组合。
4. **错误码不能跨并发窗口传递**。全局 `errno` 在 SMP 下会被其他执行流覆盖，且封装函数内部可能污染它；稳定结果应在真实错误产生点保存。
5. **调试手段要按“现象 → 缩小范围 → 取证 → 定位调用链”的顺序使用**：命令矩阵用于判定行为分支，抓包（HCI/DMA 侧）用于确认协议层真实流量，调用链追踪用于定位责任层，调用栈回溯用于定位运行时上下文，硬件寄存器/GPIO 操作用于验证底层动作是否真实发生。
6. **权限受限时先做只读取证**。只读命令（状态查询、属性读取、ping、日志导出）通常不受限，能形成有效证据；写操作被拒时把报错原文留档并给出待复验项，比盲目重试更有价值。
7. **提交前必须自查改动范围**：`git status` / `git diff` 确认只包含必要文件，提交信息包含问题单号与平台，推送前用 `git show` 复核 diff，避免把无关改动带入评审。
